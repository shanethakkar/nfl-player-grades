# Rosters exploration (2026-04-23)

Field notes from running `pipeline/scripts/explore_rosters.py` against
`nflreadpy 0.1.5` for seasons 2024 and 2025. Used to design
`ingest/rosters.py` (B3 / C1).

> Re-run `python scripts/explore_rosters.py` if upstream schemas seem to
> have shifted; update this doc with a new dated section rather than
> editing in place.

## TL;DR

- `load_players()` is the **player master** (24,377 all-time, `gsis_id`
  unique, draft + biographical info).
- `load_rosters(seasons=[...])` is the **end-of-season snapshot** —
  one row per `(season, team, gsis_id)`. **Does not show traded players
  on multiple teams** (~0 multi-team rows in the seasonal view).
- `load_rosters_weekly(seasons=[...])` shows the **trade history** —
  420 players in 2024 alone appeared on >1 team across the season.
- Our schema's `position TEXT NOT NULL` (no CHECK constraint) gives us
  freedom to define our own canonical position taxonomy at write time.

## Data shapes

| Source | 2024 rows | 2025 rows | Cols | Grain |
|--------|-----------|-----------|------|-------|
| `load_players()`        | — | — (24,377 all-time) | 39 | one row per player ever |
| `load_rosters([Y])`     | 3,216 | 3,137 | 36 | one row per `(season, team, gsis_id)`, end-of-season |
| `load_rosters_weekly([Y])` | 46,579 | — | 36 | one row per `(season, week, team, gsis_id)` |

Per-team roster size: 105–115 players (active + IR + practice squad +
cut-during-season).

| RET | 46 | Retired mid-season |

**Implication for grading:** keep all statuses in `player_seasons`, but
treat **ACT + INA + RES** as the eligible pool when computing snap
thresholds and `qualified` flags. DEV (practice squad) and CUT players
may have zero on-field samples.

## Position fields

`load_rosters` has **two position columns**:

- `position` — broad group (QB, RB, WR, TE, OL, DL, LB, DB, K, P, LS).
- `depth_chart_position` — specific (T, G, C within OL; CB, FS, SS within
  DB; etc.).

`load_players` has **three**:

- `position` — specific (e.g., NT, DT, DE).
- `position_group` — broad group (QB, RB, WR, TE, OL, DL, LB, DB, ST, SPEC).
- `ngs_position` — NGS-style label (only ~20% present).

### Canonical taxonomy for our pipeline

To match the grading methodology (`docs/methodology.md`) we need finer
grain than the broad group on the defensive side. Mapping rule:

| Our `position` | Source                                                    |
|----------------|-----------------------------------------------------------|
| `QB`           | `position_group == 'QB'`                                  |
| `RB`           | `position_group == 'RB'` (FB included)                    |
| `WR`           | `position_group == 'WR'`                                  |
| `TE`           | `position_group == 'TE'`                                  |
| `OL`           | `position_group == 'OL'`                                  |
| `iDL`          | `position_group == 'DL'` AND `position` in {NT, DT, DI}   |
| `EDGE`         | `position_group == 'DL'` AND `position` in {DE, OLB-edge} |
| `LB`           | `position_group == 'LB'`                                  |
| `CB`           | `position_group == 'DB'` AND `position == 'CB'`           |
| `S`            | `position_group == 'DB'` AND `position` in {S, FS, SS, DB}|
| `K`            | `position_group in {'ST','SPEC'}` AND `position == 'K'`   |
| `P`            | `position_group in {'ST','SPEC'}` AND `position == 'P'`   |
| `LS`           | `position_group in {'ST','SPEC'}` AND `position == 'LS'`  |

The DL → iDL/EDGE split is the only nontrivial decision. We'll codify it
as a small lookup table in `ingest/_positions.py` and lock it down with
unit tests on representative players (e.g., Aaron Donald → iDL, Myles
Garrett → EDGE).

## ID landscape

| ID            | Coverage in `players` | Notes |
|---------------|-----------------------|-------|
| `gsis_id`     | 100% (24,377/24,377)  | Canonical join key. **Use this everywhere.** |
| `esb_id`      | 100% (24,377/24,377)  | Backup; format `XXX######`. |
| `smart_id`    | 100%                  | UUID format; nflverse internal. |
| `pfr_id`      | 92%                   | For joining PFR-derived stats later. |
| `nfl_id`      | 47%                   | Skip; too sparse. |
| `pff_id`      | 50%                   | Skip unless we add PFF integration. |
| `espn_id`     | 68%                   | Skip; not needed. |

In `load_rosters`, `gsis_id` has 0.06% nulls (~4 rows in 2024+2025) —
those are typically practice-squad or just-signed players. We **drop
them at ingest** since we have no stable join key.

## Source-of-truth split

| Field                      | Source              | Why |
|----------------------------|---------------------|-----|
| `players.full_name`        | `load_players.display_name` | More canonical than rosters' `full_name` |
| `players.position`         | derived from `load_players.position_group + position` (mapping above) | Most recent season's listed position |
| `players.birth_date`       | `load_players.birth_date` | Time-invariant |
| `players.height_inches`    | `load_players.height` | inches as float; cast to int |
| `players.weight_lbs`       | `load_players.weight` | lbs as float; cast to int |
| `players.draft_year`       | `load_players.draft_year` | More complete than rosters (49% vs 58% present) |
| `players.draft_round`      | `load_players.draft_round` | Same |
| `players.draft_pick`       | `load_players.draft_pick` | Same |
| `players.current_team_id`  | `load_players.latest_team` → `team_aliases` → `teams.team_id` | Free; no lookup of "latest season" needed |
| `player_seasons.team_id`   | `load_rosters.team` → `team_aliases` → `teams.team_id` | End-of-season team |
| `player_seasons.position_played` | derived from `load_rosters.position + depth_chart_position` | Per-season; may differ from master |

## Trade handling (deferred to v1.5)

`load_rosters` returns each player's end-of-season team only. To
distinguish "Davante Adams, Raiders" from "Davante Adams, Jets" within
2024, we need `load_rosters_weekly`. For v1, we accept the coarser
end-of-season view: `player_seasons` rows are keyed by the team a player
finished the season on. Trade-aware splits land in a follow-up migration
(would add a `joined_week` / `left_week` to `player_seasons` or a new
`player_team_stints` table).

## Things in `load_rosters` we don't need

- All the alternate IDs (`espn_id`, `sportradar_id`, `yahoo_id`,
  `rotowire_id`, `pff_id`, `fantasy_data_id`, `sleeper_id`) — useful
  only for fantasy integrations we're not building.
- `headshot_url` — premature; UI can fetch via gsis_id later if needed.
- `college` — out of scope for grading.
- `week`, `game_type`, `status_description_abbr` — these are confusing in
  `load_rosters` (they refer to the snapshot week, ~final regular-season
  week, not anything player-specific). Ignore.

## Open questions

1. **2025 row count is 3,137 vs 2024's 3,216.** Likely just because the
   2025 season is in-progress; CUT/DEV churn lower so far. Confirm late
   in season.
2. **`position_group` value `SPEC` vs `ST`.** `load_players` uses
   `'SPEC'` for specialists per spot-checks; `load_rosters` only has
   broad groups (no separate ST bucket — K/P/LS land in their own
   1-letter codes in `position`). Mapping needs both branches.
3. **DL → iDL/EDGE list completeness.** The mapping is based on common
   `position` codes; players with weird PFR/NFL labels (e.g., "OLB" used
   for edge rusher) need a fallback. Plan: when the mapping returns
   `unknown` for a DL player, log a warning with their gsis_id so we can
   manually classify.
